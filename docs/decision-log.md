# Decision Log

> **「なぜこうなっているか」より「なぜそうしなかったか」の方が失われやすい。**
> 半年後に同じ検討を繰り返さないための記録。却下案こそ丁寧に残す。

記録形式: Status / 比較した案 / 採用理由 / **却下理由** / 将来見直す可能性 / パフォーマンス影響 / 保守性影響

## Status の定義

| Status | 意味 |
|---|---|
| **Proposed** | 提案済み。CEOレビュー待ち |
| **Accepted** | 承認され、現在有効 |
| **Rejected** | 検討したが採用しなかった |
| **Deprecated** | かつて採用したが、現在は無効。**削除せず残す**(なぜ変わったかが最も重要な情報のため) |

`Deprecated` を削除しない理由: 「昔これを試してやめた」という事実が失われると、**半年後に同じ案を再提案して同じ失敗を繰り返す。**

## D-001 鷹を実体として見せない（Silent Gaze）

| | |
|---|---|
| **Status** | **Accepted**(2026-07-28 CEOレビュー承認) |
| **比較した案** | ① 鷹の全身を3Dで飛ばす ② 実写風の鷹映像 ③ **視線として抽象化(採用)** |
| **採用理由** | 「見通す」という社名の意味は、鷹という**生き物**ではなく**視線**にある。抽象化した方が意味論的に正確 |
| **却下理由** | ①② は MidJourney / Sora 的な「AI生成トレーラー」の映像文法そのもので、**2026年時点では安っぽく見える**。加えて Cadillac / Aston Martin など猛禽エンブレムの自動車ブランドが既に多く、模倣に見えるリスクがある |
| **見直し可能性** | 低。ブランドの根幹(変更不可の5項目) |
| **性能** | 有利(3Dモデル不要) |
| **保守性** | 有利(アセット依存が減る) |

## D-003 mix-blend-mode は screen ではなく lighten

| | |
|---|---|
| **Status** | **Accepted**(2026-07-28 CEOレビュー承認) |
| **比較した案** | ① アルファ抜き前処理 ② `screen` ③ **`lighten`(採用)** |
| **採用理由** | 素材が白線画/純黒背景のため、`lighten = max(a,b)` で黒が透過する。**同一画像が重なっても値が変わらず、レイヤー分割しても継ぎ目が原理的に出ない** |
| **却下理由** | ① は全素材に手作業が発生。② `screen` は `1-(1-a)(1-b)` のため中間調が重なると明るくなり、**羽根の階調が白飛びして縦帯状の継ぎ目になった(実測で確認)** |
| **見直し可能性** | 低 |
| **性能** | 同等 |
| **保守性** | 有利(前処理工程が不要) |

## D-006 Color System を High Gloss Mono 5色のみに

|---|---|

| **比較した案** | ① 暖色寄りの黒+オフホワイト ② 中間色を内挿して9段のランプを作る ③ **5色のみ・明暗2モード反転(採用)** |
| **採用理由** | 画面を DARK / LIGHT の2モードに分け、**同じ色が両モードで別の役割を担う**構造にしたことで、中間色なしで全階層を表現できた。5色すべてに役割があり、余りが無い |

| **見直し可能性** | 低(変更不可の5項目) |

## D-007 LIGHT区間で3Dを止める

| | |
|---|---|
| **Status** | **Accepted**(2026-07-28 CEOレビュー承認) |
| **比較した案** | ① 明背景でも3Dを描き続ける ② 明部だけ線画を黒転させる ③ **3Dをフェードアウト(採用)** |
| **採用理由** | 加算合成のため**明部では白い線画が原理的に見えない**。描き続ける意味がない。止めることで「暗闇=空間と発見 / 光=情報と行動」の役割分担が生まれ、Buy/Sell/Find の可読性とINPが同時に上がる |

| **性能** | **有利**(ページ後半でGPUを解放できる) |
| **保守性** | 有利 |

## D-008 Hero に Three.js を使わない

| | |
|---|---|
| **Status** | **Accepted**(2026-07-28 CEOレビュー承認) |
| **比較した案** | ① Three.js ② **SVG + CSS + Canvas2D(採用)** ③ Shader単体 |
| **採用理由** | Heroで表現するのは「まだ像を結ばない視界」であり、**奥行きよりも"にじみ"と"粒"が主題**。SVGフィルタとCanvas2Dで十分かつ高品質に作れる。SVGはロゴと同じ言語なのでブランド的にも整合する |
| **却下理由** | ① はファーストビューでWebGL初期化が走り**LCPを直撃**する。さらに Vision 以降で本格的な3D空間が動くため、**WebGLコンテキストが2つになる** — これは既に自己申告済みの設計負債(`VisionScene` + `Atmosphere` の2重起動)と同じ過ちを意図的に繰り返すことになる。③ もWebGL前提なので①と同じ問題 |
| **見直し可能性** | 中。Heroの要件が「奥行きのある空間」に変わったら再検討。その場合は Atmosphere のコンテキストを共有する形にする |
| **性能** | **有利**(WebGLコンテキスト0 / 追加JS 10KB以下) |
| **保守性** | 有利(DOMなので状態がDevToolsで読める) |

## D-011 WebGL Canvas の2重起動を統合しない（保留）

| | |
|---|---|
| **Status** | **Proposed**（要CEO判断・Phase 6で保留） |
| **比較した案** | ① `VisionScene` を廃し `Atmosphere` に統合 ② **統合せず2つのまま残す(暫定採用)** ③ Vision専用の描画をAtmosphere内に複製 |
| **採用理由** | **①を実行すると Vision の見た目が必ず変わる。** 両者はフォグの枚数・不透明度・配置・カメラ挙動が異なり、統合後に元と同一の絵を再現することは事実上できない。Baseline が差分を検出し、決定事項4「Visionは変更しない」に抵触する |
| **却下理由** | ③は同じ描画を2箇所に持つことになり、負債の形を変えただけで解消にならない |
| **見直し可能性** | **高い。** CEOが「Visionの見た目が多少変わってもCanvas統合を優先する」と判断すれば①を実行できる |
| **性能** | **不利のまま。** WebGLコンテキスト2つ、GPUメモリ二重消費。Performance Budget の「Canvas数 1」に違反している |
| **保守性** | 不利。3D描画のロジックが2箇所に分散したまま |

**これは決定事項どうしの衝突である。**

- 決定事項4「Visionは変更しない」
- Performance Budget「WebGLコンテキスト数 1」

Charter上、決定事項(変更不可)が優先されるため、**現時点では Vision を守り、負債を残す判断をした。**
ただしこれは**性能予算の明確な違反**であり、放置してよい状態ではない。

**CEOに判断を仰ぐ選択肢**

| 案 | 得るもの | 失うもの |
|---|---|---|
| A. 現状維持 | Visionの見た目が完全に保たれる | Canvas 2つ / GPU二重消費 / 予算違反が残る |
| B. 統合を許可 | 予算を満たす / 保守性向上 | Visionの霧の見え方が変わる（Baselineで差分を可視化した上で判断可能） |
| C. Vision専用Canvasを軽量化 | 中間解。負荷は下がる | 見た目は多少変わる。負債の構造は残る |

**推奨はB。** Vision の霧は「視界が開く」体験の器であって、
特定のフォグ配置そのものがブランドの根幹ではない。
Baseline で変更前後を並べて確認できるため、**見た目の劣化がないことを確認した上で統合できる。**
