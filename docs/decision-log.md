# Decision Log

> **「なぜこうなっているか」より「なぜそうしなかったか」の方が失われやすい。**
> 半年後に同じ検討を繰り返さないための記録。却下案こそ丁寧に残す。

記録形式: Status / 比較した案 / 採用理由 / **却下理由** / 将来見直す可能性 / パフォーマンス影響 / 保守性影響

## Status の定義

| Status | 意味 |
|---|---|
| **Proposed** | 提案済み。CEOレビュー待ち |
| **Accepted** | 承認され、現在有効 |
| **Rejected** | 検討したが採用しなかった |
| **Deprecated** | かつて採用したが、現在は無効。**削除せず残す**(なぜ変わったかが最も重要な情報のため) |

`Deprecated` を削除しない理由: 「昔これを試してやめた」という事実が失われると、**半年後に同じ案を再提案して同じ失敗を繰り返す。**

## なぜ統合しないのか

**統合が解こうとしていた問題（fps未達）が、統合以外の手段で解けたため。**

この判断は「Visionを守るために予算違反を我慢する」ではない。
**統合の目的だった性能改善は既に達成されており、統合しても得られるものがほとんど残っていない。**

| | 統合前（着手時） | 現在 | 予算 |
|---|---|---|---|
| desktop FPS | 52.0 | **58.2** | ≥55 ✓ |
| tablet FPS | 60.1 | **60.0** | ≥40 ✓ |
| mobile FPS | 60.1 | **60.1** | ≥40 ✓ |
| 総転送量 | 2526KB | **1037KB** | ≤1229KB ✓ |
| Baseline | — | **15/15 が 0px** | 0px ✓ |
| WebGLコンテキスト数 | 2 | 2 | 1 ✕ |

fpsは **[D-018](#d-018-画面外の3dを止めることでfpsを解決した)（画面外の3D停止）** で解決した。
Visionは1画面分しかないのに常時フルビューポート(2520×1575)を描き続けており、
常設のAtmosphere(2160×1350)と合わせて毎フレーム6.9M画素を塗っていた。
**見えていない間だけ止めれば、見た目を1pxも変えずに済む。**

## 統合で残る効果（実測）

Vision の3Dを完全に停止した状態＝**統合の理論上限**を実測した。

| | 全体 | top | vision | 他区間 |
|---|---|---|---|---|
| 現状 | 58.2 | 52 | 52 | 60 |
| Vision 3D 完全停止（上限） | 59.9 | 61 | 60 | 60 |
| **統合で得られる余地** | **+1.7** | **+9** | **+8** | **±0** |

しかも上記は「Visionの霧を消した」場合の数字であり、
**統合しても霧の描画自体は残るため、実際の改善はこれより小さい。**

## 失うもの（統合した場合）

| 項目 | 現在 | 統合後 | 影響 |
|---|---|---|---|
| camera | fov 55 / z=2 / far 120 | fov 58 / z=6 / far 220 | **透視が変わり霧の奥行きが変わる** |
| fog | FogExp2 `#000000` density 0.032 | `#050506` density 0.014 | **沈み方が変わる** |
| post-process | **なし** | Bloom / DOF / Noise / Vignette | **霧にブルームとボケが乗る** |
| dpr | 1.75 | 1.5 | 解像度が落ちる（実測で差分が出ることを確認済み） |
| 描画範囲 | Visionセクション内に clip | **全画面固定** | **霧が前後セクションへ滲む**ため別途フェード処理が必要 |

[D-012](#d-012) が許容した差分は **0.102〜0.142%**。上記はいずれもこれを大きく超える。

## 比較した3案と結論

| 案 | 得るもの | 失うもの | 判定 |
|---|---|---|---|
| **A. 統合しない（採用）** | Visionの見た目が完全に保たれる（Baseline 0px）/ 実装がそのまま | コンテキスト数2が残る / Hero・Vision区間が52fps | **採用** |
| B. 統合する | 全体 +1.7fps / Hero・Vision区間 +8〜9fps / コンテキスト数1 | 上表のとおり **Visionの見た目が確実に変わる** / 滲み対策の追加実装 | 却下 |
| C. Vision専用Canvasを軽量化 | 中間解。負荷は下がる | 見た目は変わるのに**コンテキスト数2は解消しない**＝両方の悪いところ取り | 却下 |

**Bを却下した理由**: 予算のうち**fpsと転送量は既に達成済み**で、残るのは「コンテキスト数」という*手段*の指標だけ。
手段の指標を満たすために、決定事項4が守っている*結果*（Visionの見え方）を差し出すのは順序が逆。

**Cを却下した理由**: 見た目を変えるコストを払うのに、予算違反は解消されない。**負債の形を変えるだけ。**

## 将来これを見直す条件

以下の**いずれか**が起きたら再検討する。

1. **Hero / Vision 区間が実測で 55fps を下回った場合** — 今は52fpsで、全体平均58.2に支えられて予算内に収まっている。ここが単独で予算判定の対象になったら統合が最有力手段になる
2. **Vision の設計変更が別の理由で決まった場合** — 見た目を変える許可が既に出ているなら、統合のコストは実質ゼロになる
3. **GPUメモリが実測で予算(180MB)を超えた場合** — 現在は未計測。コンテキスト2つ分のフレームバッファが効いてくる
4. **モバイルの実機（Playwrightのエミュレーションではなく）で 40fps を下回った場合**

**再検討する場合の前提**: 統合は必ず `docs/baseline/` との差分を取りながら行い、
差分が [D-012](#d-012) の許容(0.14%)を超える場合はCEO判断を仰ぐこと。

## 計測上の注意（同じ誤りを繰り返さないため）

**`canvas` をDOMから削除しても R3F の描画ループは止まらない。**
当初この方法で寄与を測り「統合の効果は +0.3fps」と**誤った見積もり**を出した
（除去したのにfpsが下がるなど不整合が出て発覚）。
**描画を止めるなら `frameloop` を切ること。** 正しい方法で測り直した結果が上表の +1.7fps。

## D-012 性能のために Baseline を更新した（Vision の背景が0.1%変化）

| | |
|---|---|
| **Status** | **Adopted**（2026-07-30 CEO決裁により新Baselineを正式採用。0.1〜0.14%の差分を許容） |
| **比較した案** | ① dpr 2 のまま維持し Vision を完全に保つ ② **dpr 1.5 に下げ Baseline を更新(採用)** ③ Vision区間だけ dpr を切り替える |
| **採用理由** | dpr 2 では **desktop 16fps**。Experience KPI の「スクロールが滑らか」を満たせず、**体験そのものが壊れる**。dpr を 1.5 に下げ、DOFを半解像度、色収差を無効化した結果 **desktop 54fps / tablet 61fps / mobile 61fps** まで回復した。副作用は Vision の背後に透ける Atmosphere の霧が **0.102〜0.142% 変化**すること。**知覚できない差**である |
| **却下理由** | ①は16fpsのまま。**0.1%の不可視な差を守るために全体験を犠牲にするのは本末転倒。** ③は同一空間でdprが切り替わり、セクション境界で解像度が変わって目に見える段差が出る |
| **見直し可能性** | 中。GPU性能の高い環境では dpr を上げる条件分岐を入れる余地がある |
| **性能** | **desktop 16→54fps（3.4倍）** |
| **保守性** | 影響なし |

**Vision変更禁止との関係**

決定事項4は「Visionを変更しない」であり、これは**Visionの設計・演出を勝手に作り替えない**という趣旨と解釈した。
今回変えたのは Vision のコードではなく、**背後に透ける共通3D空間の描画解像度**であり、
Vision自体のフォグ配置・カメラ挙動・テキスト演出は一切触っていない
（`VisionScene.tsx` の dpr は 1.75 のまま据え置き、これを変えると差分が大きく出ることを実測で確認した上で戻した）。

**~~判断を仰ぎたい点~~ → 決着**: 2026-07-30、CEO決裁により**この解釈で確定**。
新Baselineを正式採用し、0.1〜0.14%の差分を許容する。dpr 2 へは戻さない。

### 実装中に踏んだ罠（3件・いずれも実測で発覚）

1. **明滅が Opening 中に走ってH-01と不透明度を奪い合った。**
   `delay` はページ読み込みからの経過で消化されるが、入場タイムラインは Opening 完了まで一時停止している。
   結果、仕様の振幅0.06に対し**実測0.397**になり、線の不透明度も0.5に届かなかった。
   → 明滅は `paused` で作り、`tl.eventCallback("onComplete")` で再生する。
2. **`pathLength="1"` が効かず線が破線になった。**
   `vectorEffect="non-scaling-stroke"` と併用すると dash がスクリーン空間で計算され、正規化が無効になる。
   → dash はpxで扱い、`getBoundingClientRect` から実描画長を測って区間をpxへ変換する。`resize` で測り直す。
3. **`strokeLinecap="round"` が H-06 の終端で光の粒として残った。**
   長さ0へ収束したとき丸いキャップだけが点として残る。→ `butt` に変更。実測で終端の可視長 0.0px を確認。
